# Food-truck and collection evidence in the candidate

September 14, 2026. Preimplementation record. Scope: local experiment, not resident activation or release.

The experimental answer flow currently drops every food-truck and waste need even though the resident system has working adapters. That prevents a fair replacement comparison and can discard the useful half of mixed schedule/rule questions. Reuse the actual profile-configured adapters and existing evidence contracts; do not reproduce their parsers or replace working resident behavior.

Before: these live needs become capability gaps without a fetch. After: a validated food-truck day request can contribute a dated official listing; a validated collection request can contribute service-area pickup dates from the existing public-reference adapter. These remain operational evidence, never governing rules. Another part of the question can still use the approved rule/process sources.

Food-truck scope: one explicit resolved day within the configured calendar horizon. The existing feed supplies listings and may not supply readable menus. Preserve the schedule when menu enrichment is unavailable, but include no menu or price claims. An unspecified next truck or multi-day request remains an explicit integration gap at this step; it must not silently become today. The original healthy-empty/parser-failure distinction and exact configured source URL remain enforced.

Collection scope: explicitly selected garbage/recycling service, a copied profile service-area name where supplied, and one starting day (today if no resident date). Reuse only the existing published public-reference logic; never query a resident address, invent an area, substitute another community, or add offsets. The returned dates are next pickup on or after the starting day, not proof of a pickup on that day or proof of no holiday delay. Do not project the unbound holiday-note string as independently verified status. Missing/unproven area or provider failure remains a gap. Existing official handoff coverage must be checked separately before adoption.

Shared software validates connector identity, service/date/area binding, exact configured schedule source, current observation/expiry and dated claims before giving the writer evidence. Raw fetched text, URLs or requests from the model cannot supply facts. A failed connector must leave successful independent evidence available. Profiles own endpoints, labels, public references and date policies; no community facts or URLs enter the experimental bridge.

Date scoping requirement: a date elsewhere in a compound question must not implicitly become the starting day for every need. An empty collection date binding starts today; an empty food date binding is unresolved. Preserve the existing deterministic correction of a copied prior date for single-need follow-ups. Test a tomorrow food request alongside an undated recycling request before comparing the mixed flow.

Validation: actual-parser synthetic tests for two community identities; copied and invented area/date checks; schedule versus menu/permission/delay collisions; missing and malformed sources; failed menus with valid schedules; expiry and wrong-host/scope rejection; mixed rule/live retrieval. No paid calls are needed for this implementation step. Later repeated model/full-answer trials and complete costs are still required; this does not establish the acceptance targets.

Documentation: precise local pending Notion addition under the existing external-write rejection. Experimental flow only; resident diagram and UI unchanged. Record implemented and verified-local states separately from any later release.
